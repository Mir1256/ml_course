## 1. Зачем это нужно

Типичная история: человек ставит `pip install torch`, видит `torch.cuda.is_available() == True` и неделю учит модель… на CPU. Или получает `CUDA error: no kernel image is available for execution on the device` в середине эпохи. Обе ситуации — про окружение, а не про ML.

С твоей **GTX 1050 Ti** окружение особенно важно. В 2026 году эта карта (архитектура Pascal) находится на краю поддержки:
- **драйвер:** последняя ветка драйверов NVIDIA для Pascal на Linux — **580**. В ветке 590 поддержка GTX 10xx убрана;
- **PyTorch:** сборки под CUDA 12.8 и CUDA 13 (то, что ставит обычный `pip install torch`) ядер для Pascal не содержат. Подходит только сборка **cu126**, и последняя версия PyTorch с ней — **2.14**.

Цель урока: одно окружение, в котором `.py`-скрипты, pytest и Jupyter-ноутбуки в VS Code видят один и тот же Python и реально считают на GPU.

## 2. Интуиция: слои стека

```
 ┌─────────────────────────────────────────────┐
 │ твой код / ноутбук                           │
 ├─────────────────────────────────────────────┤
 │ PyTorch 2.14 (+cu126)  ← внутри колеса уже   │  виртуальное окружение .venv
 │ лежат CUDA runtime, cuBLAS, cuDNN            │  (у каждого проекта своё)
 ├─────────────────────────────────────────────┤
 │ драйвер NVIDIA 580 (ядро Linux)              │  системный, один на машину
 ├─────────────────────────────────────────────┤
 │ GPU GTX 1050 Ti, Pascal, sm_61, 4 ГБ         │  железо
 └─────────────────────────────────────────────┘
```

Аналогия: драйвер — это дорога, CUDA runtime в колесе PyTorch — машина, а `sm_61` — тип колеи. Машина, собранная под другую колею (`sm_75+`), до трассы доедет (`is_available() == True`), но поехать не сможет (`no kernel image`).

**Главное следствие:** ставить CUDA Toolkit в систему для PyTorch **не нужно**. Колесо PyTorch приносит свой CUDA runtime. Нужен только драйвер, который не старше требований этого runtime. Для CUDA 12.x на Linux достаточно драйвера ≥ 525, а 580 подходит с запасом.

**Виртуальное окружение** — изолированная копия интерпретатора со своими пакетами. Для C#-разработчика ближайшая аналогия — отдельный набор NuGet-пакетов на проект. Только в Python по умолчанию всё ставится глобально, поэтому изоляцию нужно включать самому.

**uv** — быстрый менеджер пакетов и окружений (Astral, тот же автор, что у `ruff`). Он заменяет связку `pip + venv + pip-tools` и пишет lock-файл. Lock-файл фиксирует точные версии всех зависимостей, так что окружение воспроизводится через год.

## 3. Как это устроено (вместо математики)

**Compute capability.** Каждое поколение GPU NVIDIA имеет номер архитектуры: Pascal = 6.x (у 1050 Ti — 6.1, `sm_61`), Volta = 7.0, Turing = 7.5, Ampere = 8.x, Ada = 8.9, Blackwell = 10.x/12.x. Колесо PyTorch содержит машинный код ядер только для перечисленных при сборке архитектур. Список виден в `torch.cuda.get_arch_list()`. Если твоей архитектуры там нет — ядер нет.

**Почему колёса «худеют».** Каждая архитектура добавляет к колесу сотни мегабайт, а у PyPI есть лимит размера файла. Поэтому старые архитектуры постепенно выкидывают: в сборках cu128 (PyTorch 2.8) — Pascal и Maxwell, в CUDA 13 они не поддерживаются вовсе.

**Асинхронность GPU.** Вызов `a @ b` на GPU только ставит ядро в очередь и сразу возвращает управление. Поэтому замер времени без `torch.cuda.synchronize()` покажет ~0 мс. Это первая «ловушка бенчмарка», она встретится ещё много раз.

**Сколько это в цифрах.** Матричное умножение $n \times n$ стоит $2n^3$ операций с плавающей точкой (на каждый из $n^2$ элементов результата — $n$ умножений и $n$ сложений). Для $n = 2048$ это ≈ 17,2 GFLOP. Пиковая FP32-производительность 1050 Ti — около 2 TFLOPS, значит в идеале ≈ 9 мс. Реально выходит 60–80% пика.

**FP16 на Pascal.** Тензорных ядер у Pascal нет, а FP16-арифметика на чипе GP107 работает в десятки раз медленнее FP32. Поэтому смешанная точность (AMP), которая на современных картах ускоряет обучение в 2–3 раза, тебе ускорения не даст. Обучаем в FP32 (подробно — урок 67).

## 4. Установка шаг за шагом (Linux Mint)

### 4.1. Драйвер NVIDIA 580

1. **Менеджер драйверов** (Driver Manager) → выбрать `nvidia-driver-580` (recommended для GTX 1050 Ti). Не ставь 590+ — они не поддерживают Pascal.
2. Перезагрузка.
3. Проверка:

```bash
nvidia-smi
```

В шапке должно быть `Driver Version: 580.xx`, в таблице — `GeForce GTX 1050 Ti` и `4096MiB`. Колонка `CUDA Version` показывает **максимальную** версию CUDA, которую поддерживает драйвер. Это не значит, что CUDA установлена.

### 4.2. uv и Python 3.11+

```bash
curl -LsSf https://astral.sh/uv/install.sh | sh
```

Затем, из папки `ml_course` (в ней уже лежит [pyproject.toml](../../pyproject.toml)):

```bash
uv python install 3.12
```

```bash
uv sync
```

`uv sync` создаёт `.venv`, ставит все зависимости и пишет `uv.lock`. Самое важное место в `pyproject.toml` — привязка torch к индексу cu126:

```toml
dependencies = [ ..., "torch==2.14.*", "torchvision==0.29.*" ]

[[tool.uv.index]]
name = "pytorch-cu126"
url = "https://download.pytorch.org/whl/cu126"
explicit = true            # индекс используется ТОЛЬКО для пакетов, явно указанных ниже

[tool.uv.sources]
torch = { index = "pytorch-cu126" }
torchvision = { index = "pytorch-cu126" }
```

Без `explicit = true` uv искал бы в индексе PyTorch и numpy, и всё остальное. Без `[tool.uv.sources]` torch пришёл бы с PyPI в сборке под CUDA 13, и карта перестала бы работать.

Если uv не хочется, эквивалент на pip:

```bash
python3.12 -m venv .venv && source .venv/bin/activate
```

```bash
pip install "torch==2.14.*" "torchvision==0.29.*" --index-url https://download.pytorch.org/whl/cu126
```

### 4.3. VS Code + Jupyter

2. `Ctrl+Shift+P` → *Python: Select Interpreter* → `ml_course/.venv/bin/python`.

        _ = a_gpu @ b_gpu                      # прогрев: первая операция инициализирует CUDA-контекст

## 6. Типичные ошибки и как их отлаживать

| Симптом | Причина | Что сделать |
|---|---|---|
| `torch.__version__` = `2.x.x` без `+cu126`, а `torch.version.cuda` = `None` | Поставилась CPU-сборка с PyPI | Проверить `[tool.uv.sources]`, затем `uv sync --reinstall-package torch` |
| `no kernel image is available for execution on the device` | Сборка без `sm_61` (cu128/cu130 или torch ≥ 2.15) | Вернуться на `torch==2.14.*` из cu126 |
| `nvidia-smi: command not found` или `NVIDIA-SMI has failed` | Драйвер не установлен или не загрузился (часто — Secure Boot блокирует модуль ядра) | Менеджер драйверов → 580; при Secure Boot — подписать модуль (MOK) или отключить Secure Boot |
| Ноутбук в VS Code не видит пакеты, а скрипт видит | Ядро ноутбука — другой Python | *Select Kernel* → `.venv`; проверка `sys.executable` |
| `CUDA out of memory` на маленькой модели | 4 ГБ, часть занята рабочим столом, или «висит» старый процесс Jupyter | `nvidia-smi` → посмотреть процессы; перезапустить ядро; уменьшить batch |
| Замер времени на GPU = 0,1 мс | Не было `torch.cuda.synchronize()` | Синхронизировать до и после замера, делать прогрев |
| Обновил драйвер до 590 через `apt upgrade` — GPU пропал | В 590 нет Pascal | Закрепить пакет: `sudo apt-mark hold nvidia-driver-580` |

## Ответы на вопросы для самопроверки

1. Колесо PyTorch уже содержит CUDA runtime, cuBLAS и cuDNN нужных версий. Toolkit в системе нужен, только если компилировать свои CUDA-расширения. Драйвер — это модуль ядра ОС, который разговаривает с железом. Его нельзя положить в Python-пакет, и он должен поддерживать версию CUDA runtime из колеса.
2. Это номер архитектуры GPU (у 1050 Ti — 6.1). Колесо содержит машинный код ядер только для архитектур, перечисленных при сборке, — `torch.cuda.get_arch_list()`. Если там нет `sm_61` (и нет PTX, который драйвер может докомпилировать), ядра не запустятся.
3. `is_available()` проверяет только наличие драйвера и устройства. Есть ли в сборке ядра под твою архитектуру, выяснится при первой операции. Вдобавок модель и данные нужно явно перенести на устройство (`.to("cuda")`); без этого всё честно считается на CPU.
4. `[tool.uv.sources]` говорит, что torch и torchvision берутся из индекса cu126. Без этого они пришли бы с PyPI в сборке под CUDA 13 без Pascal. `explicit = true` запрещает искать в этом индексе всё остальное. Без него uv мог бы взять numpy или другие пакеты из индекса PyTorch, где лежат свои, иногда устаревшие копии.
5. `pyproject.toml` задаёт допустимые диапазоны и только прямые зависимости. Lock-файл фиксирует точные версии **всех** пакетов, включая транзитивные, и их хэши. Поэтому `uv sync` через год или на другой машине даст бит-в-бит то же окружение.
6. Операции на GPU асинхронны: Python ставит ядро в очередь и идёт дальше. Без синхронизации таймер измеряет время постановки в очередь, а настоящее время «всплывёт» в следующей операции, которой нужен результат (например, `.cpu()` или `.item()`).
7. У Pascal нет тензорных ядер, а FP16-арифметика на GP107 работает в десятки раз медленнее FP32. AMP экономит память, но вычисления станут медленнее или в лучшем случае не быстрее.
