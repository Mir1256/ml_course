## 1. Зачем это нужно

Модель не лучше данных, на которых учится, а данные откуда-то приходят. В реальном CV-проекте источники разные:
- **база разметки** (PostgreSQL за CVAT, Label Studio, внутренние системы) — отсюда выгружают аннотации и статистику работы разметчиков;
- **интернет** — открытые датасеты и картинки с сайтов, но с лицензиями, robots.txt и правами на изображения людей;
- **API** — метаданные: погода, расписания смен, геоданные, внешние модели;
- **мобильные приложения** — фото с телефонов с EXIF-метаданными (ориентация, время, GPS);
- **IoT** — камеры и датчики, которые шлют поток кадров и измерений с пропусками и сбоями.

У каждого источника свои ловушки. Этот урок — про то, как доставать данные надёжно и не принести вместе с ними ошибки.

## 2. Интуиция

- **Реляционная БД (SQL)** — набор таблиц со связями по ключам: `images`, `annotations`, `categories`, `annotators`. Это та же модель, что три DataFrame в уроке 22, только данные лежат на сервере, а не в памяти. SQL — язык запросов: ты описываешь, **что** хочешь получить, а СУБД сама решает, **как**.
- **NoSQL** — когда строгая схема мешает. Документные БД (MongoDB) хранят JSON-документы: «картинка со всей своей разметкой» одним объектом. Key-value (Redis) — кэш и очереди. Колоночные и time-series БД (ClickHouse, InfluxDB) — для потоков метрик и событий IoT.
- **API** — договор «пришли запрос такого вида — получишь ответ такого вида». Сеть ненадёжна, поэтому любой клиент API обязан уметь: таймауты, повторы, лимиты частоты, пагинацию.
- **Интернет-скрейпинг** — последнее средство. Сначала проверь, нет ли API или готового датасета. Потом — лицензию, robots.txt и закон о персональных данных.
- **IoT** — данные приходят **потоком**, с пропусками, задержками и сбоями датчиков. Их агрегируют по временным окнам.

## 3. Математика и устройство

### 3.1. Реляционная алгебра на одном слайде

- **JOIN** — декартово произведение двух таблиц, отфильтрованное по условию ключей. Наивно — $O(nm)$. СУБД делают его через хэш-таблицу ($O(n + m)$) или через индексы.
- **GROUP BY** — то самое split–apply–combine из урока 22.
- **Анти-JOIN** (`LEFT JOIN ... WHERE right.id IS NULL` или `NOT EXISTS`) — «строки слева, у которых нет пары справа». Картинки без разметки.
- **Оконная функция** (`... OVER (PARTITION BY ... ORDER BY ...)`) считает значение по группе строк, но, в отличие от GROUP BY, **не схлопывает** строки. Отсюда ранги внутри картинки (`ROW_NUMBER`), нарастающие итоги, сравнение с предыдущей строкой (`LAG`).

### 3.2. Индекс: почему поиск ускоряется в сто раз

Без индекса запрос `WHERE image_id = 5` читает **всю** таблицу: $O(n)$. Индекс — это **B-дерево**: сбалансированное дерево поиска с большим ветвлением (сотни потомков у узла). Высота дерева — $\log_b n$, то есть 3–4 уровня даже на миллиардах строк. Поиск — $O(\log n)$. Цена индекса — место на диске и замедление вставок: каждое добавление обновляет дерево. Индексы ставят на колонки, по которым ищут и соединяют (`image_id`, `category_id`).

### 3.3. Экспоненциальная задержка с джиттером

Сервер ответил 503 («перегружен»). Если все клиенты повторят запрос через одну и ту же секунду, они снова его перегрузят. Поэтому задержку перед $k$-й повторной попыткой делают растущей и случайной:

$$\text{delay}_k = b \cdot 2^k + U(0, b).$$

Суммарное ожидание за $K$ попыток — $\approx b(2^K - 1)$, то есть конечно и предсказуемо. Случайная добавка (jitter) разносит повторы разных клиентов во времени. Повторять имеет смысл только «временные» ошибки: 429, 5xx, обрыв соединения. Ошибка 404 или 400 при повторе не исправится.

### 3.4. Поток: окна и детекция сбоев

Поток значений $x_t$ агрегируют по окнам $[t, t + \Delta)$: среднее, мин/макс, **число** замеров. Число замеров в окне — простейший детектор потерь: при частоте 1 Гц в минутном окне ожидается 60. Залипший датчик выдаёт константу, и скользящая дисперсия за окно равна нулю. Это робастный признак сбоя, который не зависит от уровня сигнала.

## 4. Реализация

### 4.1. SQL на базе разметки

Файл: [код/sql_practice.py](код/sql_practice.py) создаёт в SQLite (встроена в Python, сервер не нужен) схему из 4 таблиц: 3000 картинок, ≈ 7500 аннотаций, 3 разметчика. Ключевые запросы:

```sql
-- JOIN + GROUP BY + HAVING
SELECT c.name AS category, COUNT(*) AS n, ROUND(AVG(a.w * a.h), 1) AS mean_area
FROM annotations a JOIN categories c ON c.id = a.category_id
GROUP BY c.name HAVING COUNT(*) > 500 ORDER BY n DESC;

-- Анти-JOIN: картинки без аннотаций
SELECT i.id FROM images i LEFT JOIN annotations a ON a.image_id = i.id WHERE a.id IS NULL;

-- CTE + оконная функция: топ-2 объекта по уверенности на каждой картинке
WITH ranked AS (
    SELECT image_id, id, score,
           ROW_NUMBER() OVER (PARTITION BY image_id ORDER BY score DESC) AS rnk
    FROM annotations)
SELECT image_id, id, score FROM ranked WHERE rnk <= 2;

-- Окно поверх агрегата: доля каждого разметчика и нарастающий итог по дням
SELECT an.name, COUNT(*) AS n, ROUND(1.0 * COUNT(*) / SUM(COUNT(*)) OVER (), 3) AS share ...
SELECT day, COUNT(*) AS n, SUM(COUNT(*)) OVER (ORDER BY day) AS cumulative ...

-- NOT EXISTS: картинки, где есть человек, но нет каски
SELECT COUNT(DISTINCT a.image_id) FROM annotations a
WHERE a.category_id = 1
  AND NOT EXISTS (SELECT 1 FROM annotations b WHERE b.image_id = a.image_id AND b.category_id = 3);
```

- Анти-JOIN и топ-2 на картинку совпали с pandas-реализацией. SQL и DataFrame — два языка для одних и тех же операций.
- `EXPLAIN QUERY PLAN` показывает решение СУБД: без индекса — `SCAN` (полный просмотр), с индексом — `SEARCH ... USING COVERING INDEX`. Ускорение в 115 раз на 7500 строках. На миллионах строк разница — секунды против часов.
- `pd.read_sql_query(sql, con)` превращает результат запроса в DataFrame. Это стандартный мост между базой и анализом.

### 4.2. Надёжный клиент API

Файл: [код/api_client.py](код/api_client.py):

```python
def get_json(session, url, params=None, *, retries=4, backoff=0.5, timeout=10.0, sleep=time.sleep):
    for attempt in range(retries + 1):
        try:
            r = session.get(url, params=params, timeout=timeout)
        except (requests.ConnectionError, requests.Timeout):
            if attempt == retries:
                raise
        else:
            if r.status_code not in RETRY_STATUS:
                r.raise_for_status()                     # 4xx (кроме 429) — ошибка запроса, повторять бессмысленно
                return r.json()
            ...
            if "Retry-After" in r.headers:               # сервер сам говорит, сколько ждать
                sleep(float(r.headers["Retry-After"]))
                continue
        sleep(backoff * 2**attempt + random.uniform(0, backoff))
```

Ещё в файле: пагинация по `offset/limit`, кэш ответов на диске и пример настоящего публичного API без ключа — [Open-Meteo](https://open-meteo.com/): почасовая температура и облачность.

2026-11-08 01:00:00             0.4           96
...

Зачем это CV: облачность и время суток объясняют освещённость кадров. Это метаданные для срезов метрик (урок 12) и для поиска причин сдвига распределения (урок 1).

`sleep` передаётся параметром не случайно. Так тесты подменяют ожидание и проверяют задержки **без реального ожидания**: тест `test_retry_then_success` за миллисекунды проверяет, что после двух ответов 503 клиент дождался успеха и задержка росла.

**EXIF-ориентация** — классическая ловушка данных с телефонов. Телефон сохраняет пиксели так, как их снял сенсор, а в тег `Orientation` пишет, как их повернуть при показе. Программы разметки (и браузер) тег учитывают, а `np.asarray(Image.open(...))` — нет. В итоге картинка повёрнута на 90°, а рамки — нет. Лечение — `ImageOps.exif_transpose` **на этапе загрузки**, одинаково при обучении и инференсе (иначе это training-serving skew из урока 1).

**Поток датчика:** обрыв связи на 100 секунд нашёлся по числу замеров в минутных окнах, «залипание» на 30 секунд — по нулевой скользящей дисперсии (30 − 10 + 1 = 21 окно целиком внутри сбоя).

## 6. Типичные ошибки и как их отлаживать

| Ошибка | Последствие | Как правильно |
|---|---|---|
| SQL через f-строку с подстановкой значений | SQL-инъекция; ломается на кавычках в именах файлов | Параметры: `con.execute(q, (value,))` |
| JOIN без проверки кратности ключей | Строки размножаются, счётчики завышены (урок 22) | `COUNT(*)` до и после; уникальные ключи; `validate` в pandas |
| `requests.get` без `timeout` | Скрипт сбора «висит» вечно | Всегда `timeout=` |
| Повтор любых ошибок | 400/404 повторяются бесконечно; сервер забанит за долбёжку | Повторять только 429/5xx/сеть; backoff + jitter; `Retry-After` |
| Скрейпинг без проверки robots.txt и лицензии | Юридические риски; картинки людей — персональные данные | Сначала API или открытый датасет; robots.txt, лицензия, задержки |
| Игнорирование EXIF-ориентации | Повёрнутые картинки, рамки не на объектах | `ImageOps.exif_transpose` при загрузке |
| Среднее по окну без числа замеров | Окно с одним замером выглядит как нормальное | Всегда хранить `count`; помечать неполные окна |
| Время датчиков без часового пояса | Сдвиг на часы при соединении с другими источниками | Хранить в UTC, `tz_localize`/`tz_convert` |

## Ответы на вопросы для самопроверки

1. SQL — таблицы со строгой схемой, связи по ключам, JOIN, транзакции; удобно для аналитики по разметке (счётчики, срезы, разметчики). Документные NoSQL — гибкие JSON-документы. Удобно, когда у объекта переменная вложенная структура (картинка со всей разметкой, полигонами и историей правок) и её читают целиком.
2. `SELECT c.name, COUNT(*) AS n FROM annotations a JOIN categories c ON c.id = a.category_id JOIN images i ON i.id = a.image_id WHERE i.camera = 'cam_gate' GROUP BY c.name HAVING COUNT(*) > 100;`
3. GROUP BY схлопывает группу в одну строку, оконная функция добавляет к **каждой** строке значение, посчитанное по её группе. Топ-3: `ROW_NUMBER() OVER (PARTITION BY image_id ORDER BY score DESC) AS rnk` в CTE и `WHERE rnk <= 3`.
4. Индекс — B-дерево по значениям колонки: поиск спуском по дереву за $O(\log n)$ вместо полного просмотра $O(n)$. Платим местом и замедлением вставок и обновлений.
5. Повторять — 429, 500, 502, 503, 504, обрывы соединения и таймауты (временные проблемы). Не повторять — 400, 401, 403, 404 (запрос ошибочен, повтор не поможет). Джиттер разносит повторы разных клиентов во времени, чтобы они не «били» сервер синхронно.
6. Тег, который говорит, как повернуть сохранённые пиксели при показе. Разметчик видел повёрнутую картинку и рисовал рамки на ней, а код, читающий пиксели без учёта тега, получает неповёрнутую — рамки не на объектах.
7. Обрыв — по числу замеров в окне (меньше ожидаемого по частоте). Залипание — по нулевой (или почти нулевой) скользящей дисперсии за окно.
